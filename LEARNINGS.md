- 2026-10-31 · **Tool-parser freeze.** A main-track forum bug report says the gemma4 tool parser can loop forever on an array tool argument and freeze the inference server for the rest of the run. **Reproduced offline** on vLLM 0.19.1's `vllm/tool_parsers/gemma4_tool_parser.py` (pure-Python helpers run with a 2 s watchdog thread, no GPU):
  - `_parse_gemma4_args` never returns on `nodes:[[<|"|>x]y<|"|>]]` or `nodes:[[<|"|>x[y<|"|>]]`, i.e. an array nested in an array whose string element contains `[` or `]`. The nested-array bracket counter ignores string delimiters, and the bare-value branch never advances past the stray `]`, so it appends forever.
  - Flat lists are fine, including `]` inside a string, and so are nested lists without brackets in strings. The only array argument in the harness tool set is `get_code_subgraph(nodes: list[str])`, so the trigger needs a malformed nested list from the model: rare, but possible for small models.
  - The loop runs in the API server process, so the whole server, including `/health`, stops responding.
  - Without protection a freeze burns quota until the session limit: LiteLLM's default request timeout is 6,000 s, adk-eval-core's ModelRetryPlugin retries timeouts up to 5 times, and pilot C's time guards only ran between runs.
  - **Rule for all GPU notebooks:** per-request timeouts plus a `/health` watchdog that kills the server and fails pending requests fast with a non-retryable error. Pilot C implements this in `common/server_watchdog.py` (pilot/c-bottleneck); `notebooks/build_notebooks.py` refuses to build a GPU notebook without it.
  - Source: forum report (relayed by the coordinator); offline reproduction (pilot C).
