# Pilot A: skills as weight-free post-training (branch `pilot/a-skills`)

Question: can a small library of `SKILL.md` skills change how Gemma 4 E4B behaves as a
bug-fixing agent, the way a LoRA would, and does the effect carry over to a repo the skills
were not built from (built from `rich` traces, evaluated on `fastapi`)?

Start with **[REPORT.md](REPORT.md)**. The harness facts are in [docs/HARNESS_SKILLS.md](docs/HARNESS_SKILLS.md).

| Path | What |
|---|---|
| `common/` | shared, pilot-agnostic: task loader, ATIF trace parser, shared metrics + stats |
| `pilot_a/build_submission.py` | builds an arm (baseline / skill arm / inline control) from the official sample |
| `pilot_a/skills/hand_written/` | arm 1: 3 generic skills (one with a sandbox script) |
| `pilot_a/distill_skills.py` | arm 2: Gemma turns its own failed traces into skills (runs on Kaggle) |
| `pilot_a/skills/frontier/` | arm 3: FRONTIER-WRITTEN (by Claude) from the same traces. Not yet written, needs phase-2 traces. **Never put this arm in a main-track submission.** |
| `pilot_a/plan.py`, `splits.json` | which arm/seed/tasks each phase runs (task ids only) |
| `pilot_a/kaggle_runner.py` | Kaggle-side runner (vLLM + swegemma Evaluator + metrics) |
| `pilot_a/scripts/` | local CPU checks: `inspect_prompt.py` (what the model sees), `dry_run_harness.py` (real harness, scripted model) |
| `notebooks/pilot_a_run.ipynb` | the one notebook to run on Kaggle (generated by `tools/build_notebook.py`) |
| `results/` | committed aggregate JSONs from Kaggle runs (no traces, no patches) |
| `research/log.md` | one line per GPU run, with hours |

Competition data is never committed (`.gitignore`). Local copies live in `data/` (ignored).

Local checks (CPU only):
```bash
python tests/test_common.py && python tests/test_distill.py
```
